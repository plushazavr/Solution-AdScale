# Паттерны надёжности
  
## Circuit Breaker
**Необходим на уровнях:**
1. B2B Gateway - Ad Server
2. Bidding Service - Redis
3. Bidding Service - Delivery Service 
т.е. необходим на всем hot path. 
  
**Пример параметров:**
* окно 10 сек, минимум 50 запросов, порог ошибок 50% (ошибки: **только 5xx**, таймаут, более 80 мс)
* half-open: 3–5 проб раз в 5 сек, успех 100%
* **Ошибки 4xx исключены из счётчика.** Они отражают ошибочный трафик от клиентов, а не состояние сервиса, и их включение приведёт к ложному размыканию цепи и отключению работающего сервиса
  
## Ретраи 
  
Настройка ретраев с экспоненциальной задержкой. Например: 3 попытки, задержки 100-200-400 мс, jitter 20%. Ретраим только идемпотентные вызовы, т.е. 4xx и breaker open не ретраим. Исключены для hot path, т.к. нарушают SLA менее 80 мс. 
  
## Идемпотентность
в событийной архитектуре с использованием Kafka возможны дубли запросов (при ретраях, прогреве кеша, рестарте консьюмера), поэтому необходимо:
  
* для каждого запроса необходим свой идентификатор (bid-запрос, запрос на списание платежа), который генерируется единожды продюсером
* при записи в БД необходимо учитывать наличие записи по PK (см.пункт выше), если такая запись есть в БД, то игнорировать дубль, иначе выполнить запись
  
## Резервные стратегии
  
Необходимо при росте времени ответа от БД или Redis. Bidding Service не должен ждать и нарушать SLA 80 мс.
  
**Использовать локальный кеш.** В Bidding Service держим локальный кеш топ-N кампаний по числу выигранных аукционов. Кеш регулярно обновляется. При проблемах с БД/Redis берём данные из локального кеша. **Риск:** несоответствие данных (в кеше данные отстают по обновлению). Поэтому необходимо настроить короткий TTL для записей в кеше. 
  
## Резервирование бюджета
  
Резервирование бюджета в Redis с помощью Lua-скрипта (Bidding Service → Redis): первый аукцион резервирует сумму, второй видит уже уменьшенный баланс. 
  
**Полный цикл резерва:** 
  
1. **Аукцион.** Bidding Service резервирует сумму в Redis ( Lua-скрипт, атомарно проверяет и списывает баланс). Записывает ключ резерва со статусом `pending`.
2. **Подтверждение.** Delivery Service шлёт событие показа в Kafka. Консьюмер в Financial Service находит резерв по `requestId`, переводит статус в `confirmed` и инициирует списание.
3. **Вовзврат при отсутствии показа.** Если в течение определенного времени (например 10 сек) событие показа не пришло, Financial Service переводит резерв в статус `released` и возвращает сумму в баланс через Redis Lua-скрипт.
4. **Возврат при проигрыше аукциона** Если аукцион проигран (ставка не выиграла), Bidding Service немедленно освобождает резерв статусом `released` вне очереди Kafka.
  
**Правило при отказе Redis:** без подтверждённого резерва в Redis оплачиваемую ставку DSP-партнёру выдавать **нельзя**. Если Redis вернул ошибку (timeout, connection refused, Lua error) — отдаём `no-bid`. Кредитовать ставку «в надежде» нельзя, т.к. это приведёт к списанию средств рекламодателя без гарантий оплаты за показ.
  
**Таймаут Redis:** максимальный таймаут на вызов Redis 10 мс. Это ограничение вытекает из общего SLA 80 мс на весь hot path. Таймаут Redis ограничен остатком общего deadline. После выделения 2 мс на входящий gRPC, 2 мс на исходящий gRPC и 20 мс на расчёт аукциона (с запасом ×2 для P95 40 мс), на Redis остаётся не более 10 мс на каждое из трёх обращений (чтение кампании, резерв, запись победителя).

## Протокол создания резерва

### Порядок записей до bid-response

| Шаг | Сервис | Действие | Гарантия |
| --- | --- | --- | --- |
| 1 | Bidding Service | Атомарное резервирование в Redis (Lua-скрипт): уменьшает `balance:{advertiserId}`, создаёт `reserve:{requestId}` со статусом `pending` и TTL 10 сек | Временная (volatile). Redis — кеш, не авторитетный источник |
| 2 | Bidding Service → Financial Service | gRPC-вызов `createReservation(requestId, advertiserId, amount)` | Синхронный вызов |
| 3 | Financial Service | SQL-транзакция: INSERT в `reservations` (status=`pending`) + INSERT в `outbox_events` (event_type=`reserve_pending`) | ACID. После commit — резерв зафиксирован |
| 4 | Bidding Service | Отправка bid-response DSP (winner, price) | — |

**Критическое правило:** bid-response отправляется DSP **после** commit SQL-транзакции. К моменту отправки ответа DSP резерв уже записан в PostgreSQL и Outbox.

### Что устойчиво записано до ответа DSP

| Хранилище | Запись | Гарантия |
| --------- | ------ | -------- |
| Redis | `balance:{advertiserId}` (уменьшенный), `reserve:{requestId}` (pending, TTL 10 сек) | Временная. Без резерва DSP не выдаёт креатив |
| PostgreSQL | `reservations` (status=`pending`) + `outbox_events` (event_type=`reserve_pending`) | ACID. Авторитетный источник. Восстанавливает Redis при потере |

### Transactional Outbox

Transactional Outbox — паттерн, гарантирующий, что событие в Kafka будет доставлено тогда и только тогда, когда соответствующая запись в PostgreSQL зафиксирована.

**Проблема.** При создании резерва Bidding Service отвечает DSP в течение SLA < 80 мс. Если bid-response отправлен, но событие `reserve_pending` не попало в Kafka, то при восстановлении Redis из Kafka резерв будет потерян — деньги заморожены в Redis, но не учтены в журнале.

**Решение.** Событие записывается в таблицу `outbox_events` в той же SQL-транзакции, что и резерв. После commit транзакции Outbox-Consumer доставляет событие в Kafka.

**Outbox-Consumer.** Отдельный процесс Financial Service, каждые 200-300 мс опрашивает `outbox_events` по статусу `pending`, батчами по 100 событий отправляет в `balanceTopic` (продюсер с `acks=all`), и при успешной доставке обновляет статус на `published`. Интервал 200-300 мс — баланс между нагрузкой на PostgreSQL и скоростью доставки; не влияет на SLA, т.к. Outbox не на hot path.

Если Outbox-Consumer упал после отправки, но до обновления статуса — событие будет доставлено повторно. At-least-once гарантия Kafka + идемпотентность консьюмеров (по `event_id`) защищают от дублей.

### Обработка частичного успеха

| Сценарий | Что произошло | Механизм восстановления |
| --- | --- | --- |
| Redis успешен, SQL упал | Баланс уменьшен, reserve создан, но reservations/outbox не записаны | TTL 10 сек → Financial Service обнаруживает резерв без записи в БД → возвращает баланс через `reserve_released` |
| SQL успешен, Redis упал после reserve | Reservations + outbox записаны, но Redis недоступен | Outbox-Consumer отправляет `reserve_pending` в Kafka → `RedisReplayer` восстанавливает ключ из Kafka |
| SQL успешен, Redis упал до записи победителя | Reservations + outbox записаны, но Bidding не может записать winner | Ретрай внутри SLA. Если Redis не восстановился — Circuit Breaker → `no-bid`. Таймер через 10 сек возвращает резерв |
| SQL commit успешен, bid-response потерян по сети | Reservations + outbox записаны, DSP не получил ответ | DSP отправляет дубль bid-request (идемпотентный по requestId). Bidding Service (при перезапуске) находит `reserve:{requestId}` в Redis → отправляет cached response. Если TTL истёк — `no-bid` |

### Сценарии сбоев на каждом шаге

| Точка отказа | Поведение | Восстановление |
| --- | --- | --- |
| Redis недоступен до резервирования | Circuit Breaker → `no-bid` | Ничего не записано, DSP получает `no-bid` |
| Redis упал во время Lua-скрипта | Lua атомарна — баланс не изменён | `no-bid`, ничего не записано |
| Redis упал после резервирования, до Financial Service | `reserve:{requestId}` висит с TTL | TTL истекает → баланс возвращается через `reserve_released` |
| Financial Service упал до commit SQL | Резерв не записан, outbox пуст | Аналогично предыдущему: TTL → возврат баланса |
| Financial Service упал после commit, до ответа Bidding | Reservations + outbox записаны, DSP не получил ответ | Outbox-Consumer отправляет событие в Kafka. TTL резерва обеспечит возврат, если DSP не получил ставку |
| **После bid-response, до Kafka** | Reservations + outbox записаны, bid-response отправлен, но Outbox-Consumer ещё не прочитал событие | Нормальное состояние. Outbox-Consumer прочитает и отправит в Kafka. Если Redis упадёт — `RedisReplayer` восстановит из Kafka |
| Outbox-Consumer упал перед отправкой в Kafka | Событие остаётся в `outbox_events` со статусом `pending` | При перезапуске — отправит. TTL резерва обеспечит возврат, если DSP не получил ставку |
| Kafka недоступна | Outbox-Consumer не может доставить событие | Событие остаётся `pending`. При восстановлении Kafka — доставит. TTL резерва — страховка |

## Жизненный цикл резерва и обработка поздних событий

Срок окончательного расчёта: перевод резерва в статусы `confirmed` или `released` происходит при получении события показа из Kafka. Из-за at-least-once доставки максимальное время 5-10с. Это согласованное окно расчёта с DSP. Если событие пришло в течение 10 с резерв подтверждается. Если нет, то таймер возвращает сумму в баланс.

**Позднее событие (late arrival).** Пример: показ был на 2й секунде, Kafka доставила событие на 15й. К этому времени резерв уже мог вернуться в баланс исходя из вышеописанного окна. 
**Решение:** Financial Service хранит резервы в PostgreSQL (таблица `reservations`, поле `status`). При получении события проверяется статус:

- если статус `pending`, то событие пришло вовремя. Происходит перевод резерва в статус `confirmed`, баланс списывается.
- если статус `released`, то событие пришло поздно. Данное событие логируется как `late_impression`. Списания не будет, убыток на AdScale.
- если `confirmed`, то считать дублем. Игнорируется по `event_id`.

## Восстановление резервов после потери Redis

**Проблема.** Redis хранит только ключи резервов. При восстановлении из Kafka баланс пересоберётся по последним статусам `confirmed`/`released`, но `pending`, резервы которые ещё не конвертировались, будут потеряны. Деньги забронированы, но не учтены.

**Решение.** Каждый промежуточный статус резерва пишется в `balanceTopic`:

- `operation = reserve_pending` — при создании резерва в Redis.
- `operation = reserve_confirmed` — при получении события показа.
- `operation = reserve_released` — при возврате (таймаут или проигрыш).

`balanceTopic` становится полным журналом всех состояний резерва.

**Механизм blocked_balance.** Пока согласованность не завершена, разница между балансом в Redis и PostgreSQL блокируется в поле `blocked_balance`. Сумма не участвует в расчётах аукционов. Блокировка снимается после завершения восстановления.

**Процесс восстановления:**

1. `RedisReplayer` читает `balanceTopic`, пересобирает ключи Redis (`balance:{advertiserId}`, `reserve:{requestId}`).
2. Проверка согласованности кеша и БД. Происходит сверка pending-резервов в Redis с таблицей `reservations`. Расхождения исправляются: 
    - если запись есть в БД, но нет в Redis — восстанавливается в Redis (`reserve:{requestId}` = amount, TTL = время до таймаута)
    - если есть в Redis, но нет в БД — сумма блокируется (задержка записи в БД); если TTL истёк — возвращается в баланс
    - если есть в Redis и в БД со статусом `confirmed` — резерв удаляется (рассогласование, Redis опережает БД)
3. Пока проверка не завершена и `blocked_balance > 0`, аукционы приостановлены.
