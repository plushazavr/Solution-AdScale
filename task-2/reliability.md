# Паттерны надёжности
 
## Circuit Breaker
**Необходим на уровнях:**
1. B2B Gateway - Ad Server
2. Bidding Service - Redis
3. Bidding Service - Delivery Service 
т.е. необходим на всем hot path. 
 
**Пример параметров:**
* окно 10 сек, минимум 50 запросов, порог ошибок 50% (ошибки: **только 5xx**, таймаут, более 80 мс)
* half-open: 3–5 проб раз в 5 сек, успех 100%
* **Ошибки 4xx исключены из счётчика.** Они отражают ошибочный трафик от клиентов, а не состояние сервиса, и их включение приведёт к ложному размыканию цепи и отключению работающего сервиса
 
## Ретраи 
 
Настройка ретраев с экспоненциальной задержкой. Например: 3 попытки, задержки 100-200-400 мс, jitter 20%. Ретраим только идемпотентные вызовы, т.е. 4xx и breaker open не ретраим. Исключены для hot path, т.к. нарушают SLA менее 80 мс. 
 
## Идемпотентность
в событийной архитектуре с использованием Kafka возможны дубли запросов (при ретраях, прогреве кеша, рестарте консьюмера), поэтому необходимо:
 
* для каждого запроса необходим свой идентификатор (bid-запрос, запрос на списание платежа), который генерируется единожды продюсером
* при записи в БД необходимо учитывать наличие записи по PK (см.пункт выше), если такая запись есть в БД, то игнорировать дубль, иначе выполнить запись
 
## Резервные стратегии
 
Необходимо при росте времени ответа от БД или Redis. Bidding Service не должен ждать и нарушать SLA 80 мс.
 
**Использовать локальный кеш.** В Bidding Service держим локальный кеш топ-N кампаний по числу выигранных аукционов. Кеш регулярно обновляется. При проблемах с БД/Redis берём данные из локального кеша. **Риск:** несоответствие данных (в кеше данные отстают по обновлению). Поэтому необходимо настроить короткий TTL для записей в кеше. 
 
## Резервирование бюджета
 
Резервирование бюджета в Redis с помощью Lua-скрипта (Bidding Service → Redis): первый аукцион резервирует сумму, второй видит уже уменьшенный баланс. 
 
**Полный цикл резерва:** 
 
1. **Аукцион.** Bidding Service резервирует сумму в Redis ( Lua-скрипт, атомарно проверяет и списывает баланс). Записывает ключ резерва со статусом `pending`.
2. **Подтверждение.** Delivery Service шлёт событие показа в Kafka. Консьюмер в Financial Service находит резерв по `requestId`, переводит статус в `confirmed` и инициирует списание.
3. **Вовзврат при отсутствии показа.** Если в течение определенного времени (например 10 сек) событие показа не пришло, Financial Service переводит резерв в статус `released` и возвращает сумму в баланс через Redis Lua-скрипт.
4. **Возврат при проигрыше аукциона** Если аукцион проигран (ставка не выиграла), Bidding Service немедленно освобождает резерв статусом `released` вне очереди Kafka.
 
**Правило при отказе Redis:** без подтверждённого резерва в Redis оплачиваемую ставку DSP-партнёру выдавать **нельзя**. Если Redis вернул ошибку (timeout, connection refused, Lua error) — отдаём `no-bid`. Кредитовать ставку «в надежде» нельзя, т.к. это приведёт к списанию средств рекламодателя без гарантий оплаты за показ.
 
**Таймаут Redis:** максимальный таймаут на вызов Redis — **10 мс**. Это ограничение вытекает из общего SLA 80 мс на весь hot path. Таймаут Redis ограничен остатком общего deadline: после выделения 2 мс на входящий gRPC, 2 мс на исходящий gRPC и 20 мс на расчёт аукциона (с запасом ×2 для P95 — 40 мс), на Redis остаётся не более 10 мс на каждое из трёх обращений (чтение кампании, резерв, запись победителя).
