# Паттерны надёжности

## Circuit Breaker
**Необходим на уровнях:**
1. B2B Gateway - Ad Server
2. Bidding Service - Redis
3. Bidding Service - Delivery Service 
т.е. необходим на всем hot path. 

**Пример параметров:**
* окно 10 сек, минимум 50 запросов, порог ошибок 50% (ошибки: 5xx/4хх, таймаут, более 80 мс)
* half-open: 3–5 проб раз в 5 сек, успех 100% 

## Ретраи 

Настрйока ретраев с экспоненциальной задержкой. Например: 3 попытки, задержки 100-200-400 мс, jitter 20%. Ретраим только идемпотентные вызовы, т.е. 4xx и breaker open не ретраим. Исключены для hot path, т.к. нарушшают SLA менее 80 мс. 

## Идемпотентность
в событийной архитектуре с использованием Kafka возможны дубли запросов (при ретраях, прогреве кеша, рестрате консьюмера), поэтому необходимо:

* для каждого запроса необходим свой идентификатор (bid-запрос, запрос на списание платежа), который генерируется единожды продюсером
* при записи в БД необходимо учитывать наличие записи по PK (см.пункт выше), если такая запись есть в БД, то игнорировать дубль, иначе выполнить запись

## Резервные стратегии

Необходимо при росте времени ответа от БД или Redis. Bidding Service не должен ждать и нарушать SLA 80 мс.

**Использовать локальный кеш.** В Bidding Service держим локальный кеш топ-N кампаний по числу выигранных аукционов. Кеш регулярно обновляется. При проблемах с БД/Redis берём данные из локального кеша. **Риск:** несоответствие данных (в кеше данные отстают по обновлению). Поэтому необходимо настроить короткий TTL для записей в кеше. 

## Резервирование бюджета

Резервирование бюджета в Redis с помощью Lua-скрипт (Bidding Servivce -> Redis (кеш балансов): первый аукцион резервирует сумму, второй видит уже уменьшенный баланс). Резервируется до ответа о том, что ставка выйграла. Если показ ставки не подтвердился (событие показа не пришло), то резерв возвращается. Но финальное списание выполняет только Financial Service. Если Redisвернул ошибку на резервировании, то отдаем ответ no-bid, а не берем в "кредит".
