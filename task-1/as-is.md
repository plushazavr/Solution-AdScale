# AS-IS анализ

## Исходные данные системы

| Параметр                     | Значение                                  |
| ---------------------------- | ----------------------------------------- |
| Пиковая нагрузка             | 15 000 RPS                                |
| Целевой рост (3 мес.)        | +20% → 18 000 RPS                         |
| Целевой рост (1 год)         | 50 000 RPS                                |
| Текущий P95                  | 110–120 мс                                |
| Требование SLA (текущее)     | ≤ 100 мс                                  |
| Требование SLA (DSP-партнёр) | ≤ 80 мс + штрафы                          |
| БД                           | Один инстанс PostgreSQL                   |
| Кеш / очереди                | Отсутствуют                               |
| Контейнеризация / деплой     | Нет / вручную                             |
| Архитектура                  | Гибридный монолит (C++/Go/Python/Node.js) |

### Обзор компонентов системы и их влияние на систему

| Компонент            | Язык    | Назначение                                                               | Степень влияния на систему           |
| -------------------- | ------- | ------------------------------------------------------------------------ | ------------------------------------ |
| Advertiser Dashboard | Node.js | Пользовательский интерфейс для рекламодателей                            | Не критично                          |
| Auction Engine       | C++     | Содержит бизнес-правила для обработки ставок и определения победителя    | Критично для latency                 |
| Ad Server            | C++/Go  | Приём HTTP-запросов, идентификация пользователей, подбор кандидатов      | Критично для latency                 |
| Delivery Service     | Node.js | Пользовательский интерфейс с рекламой для пользователей сайта/приложения | Критично для конечного пользователя  |
| Statistics Service   | Python  | Сбор статистических данных с пользовательских интерфесов для анализа     | Высокое для latency (write-нагрузка) |
| Financial Service    | Go      | Списание средств, выставление счетов и управление балансом               | Критично (финансовые операции)       |
| Analytics Service    | Python  | SQL-запросы к БД                                                         | Высокое для latency                  |

## Узкие места

1. Общая БД с одним инстансом
2. Нет реплик БД и разделения на чтение и запись
3. Запросы в БД (чтение, запись) идут напрямую из сервиса
4. Синхронные вызовы в БД
5. Один кластер + ручной деплой

## Точки отказа

| Точка отказа                    | Что будет при отказе                                | Степень последствий | Последствия                                             |
| ------------------------------- | --------------------------------------------------- | ------------------- | ------------------------------------------------------- |
| БД                              | Полный отказ всех компонентов на чтение/запись в БД | Критическая         | Недоступность платформы                                 |
| Auction Engine                  | Нет выбора победителя → нет bid-response            | Критическая         | Не работает аукцион                                     |
| Ad Server                       | Не принимаются bid-requests и запросы пользователей | Критическая         | Недоступность платформы                                 |
| Система в целом в рамках деплоя | Любой релиз или сбой затрагивает всю систему        | Высокая             | Рост времени простоя на время деплоя. Выше риск ошибки. |

## Архитектурные проблемы

1. Монолит с общей БД
2. Синхронные, прямые операции на БД
3. Отсутствие реплик БД
4. Синхронные вызовы в hot path    
5. Отсутствие кеширования
6. Не задокументированная архитектура

## Влияние на latency

1. Все компоненты используют одну БД → увеличивает нагрузку на БД и порождает конкуренцию за ресурсы
2. Имеется синхронное чтение БД несколькими компонентами
3. Используются тяжелые SQL-запросы в единственную БД без реплик
4. Возможны синхронные операции по записи и чтению на БД → конкуренция за ресурсы
5. Отсутсвтие кеша → каждый запрос идет в БД → увеличение число обращений к БД
