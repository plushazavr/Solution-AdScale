# ADR-002: Выделение сервиса ставок (Bidding Service) в качестве первого приоритета

**Дата:** 24.10.2026
**Статус:** Accepted

## Контекст
AdScale — гибридный монолит (C++/Go/Python/Node.js) с одной инстанцией PostgreSQL. Система работает на пределе: 15 000 RPS в пике, P95 latency 110–120 мс при требовании 100 мс. Планируется интеграция с крупной DSP-площадкой: +20% нагрузки сразу (18 000 RPS), х2 через год (50 000 RPS). SLA партнёра — P95 не более 80 мс со штрафами за деградацию latency и downtime.

## AS-IS анализ выявил ключевые проблемы

1. Auction Engine - критическое бутылочное горлышко в hot path: синхронные вызовы к PostgreSQL на каждый bid-request при SLA ≤ 100 мс.
2. Единая БД без реплик для чтения и записи
3. Нет кеша и очередей: данные читаются/пишутся из БД напрямую синхронно
4. Монолит без контейнеризации и с ручным деплоем

## Ключевые архитектурные драйверы

1. **Нагрузка:** 18 000 RPS через 3 месяца, 50 000 RPS через год
2. **Latency:** P95 менее 100 мс (текущий SLA), менее 80 мс (SLA DSP-партнёра)
3. **Доступность:** SLA 99.9%, штрафы за недоступность
4. **Сроки:** промежуточное решение через 3 месяца, целевое через год
5. **Бюджет** ограничен, полная переработка невозможна.
6. **Непрерывность** бизнеса обязательна.

## Рассматривались четыре альтернативы

1. Оставить аукцион в монолите, оптимизировать БД для чтения/записи с кешом для поддержания latency
2. Начать с выноса Statistics/Analytics (некритичные домены), Bidding Service оставить в монолите и вынести в отдельный сервис в последнюю очередь
3. Сразу переписать всю систему на микросервисы
4. Выделить Bidding Service в отдельный сервис с чтением из кеша

### Альтернатива 1. Оставить аукцион в монолите, оптимизировать БД
**Плюсы:** минимальные изменения, быстрый time-to-market, не нужна новая инфраструктура.
**Минусы:** не решает структурную проблему. Аукцион всё равно синхронно ходит в БД в hot path. Потолок масштабирования остаётся, SLA 80 мс недостижим. Конкуренция за БД с аналитикой и статистикой сохраняется.

### Альтернатива 2. Начать с выноса Statistics/Analytics
**Плюсы:** безопаснее, проще, снимает часть нагрузки с БД
**Минусы:** не решает главную проблему (latency hot path). Статистика не влияет на SLA DSP напрямую и вынос аукциона всё равно придётся делать, но позже и в сжатые сроки.

### Альтернатива 3. Сразу переписать всё на микросервисы
**Плюсы:** целевая архитектура сразу, независимое масштабирование всех доменов.
**Минусы:** невозможно за 3 месяца при ограниченном бюджете и низкой DevOps-зрелости. Нарушает непрерывность бизнеса.

### Альтернатива 4. Выделить Auction Engine (Bidding Service) с чтением из кеша
**Плюсы:** изолирует hot path, позволяет масштабировать аукцион независимо, исключает синхронные обращения к БД (чтение из Redis), создаёт фундамент для Strangler Fig, позволяет уложиться в SLA 80 мс.
**Минусы:** нужны Redis и оптимизация БД (реплики, автовостановление). Эксплуатация нового сервиса ложится на текущую команду без SRE.

## Решение
Bidding Service выделяется в отдельный сервис первым приоритетом в рамках трехмесячного горизонта. Bidding Service становится первым сервисом, вынесенным из монолита по паттерну Strangler Fig.

## Последствия

### Положительные

1. hot path изолирован, Bidding Service масштабируется независимо, читает из кеша, не конкурирует с другими компонентами за БД.
2. Появляется возможность уложиться в SLA 80 мс за счёт исключения синхронных обращений к БД.
4. Аукцион получает независимый релизный цикл и профиль масштабирования.
5. Создаётся основа для целевой архитектуры на 50 000 RPS.

### Отрицательные

1. Невозможно полностью отказаться от монолита за 3 месяца. Часть функционала остаётся в нём.
2. Дублирование логики на время миграции: часть запросов идёт в монолит, часть в новый сервис.
3. Дополнительные инфраструктурные затраты: Redis, БД, Gateway.
4. Эксплуатация нового сервиса ложится на текущую команду без выделенного SRE.

## Риски

1. Новый сервис добавляет сетевой вызов, ответ может стать медленнее
2. Кеш может быть слегка устаревшим — ставка посчитается по старому балансу
