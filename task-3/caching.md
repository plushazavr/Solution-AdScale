# Стратегия кеширования

## Что кешировать
1. Кампании
2. Бюджеты, балансы
3. Ставки на каждый аукцион
4. Победители аукциона

### Что не кешировать
1. Bid-request/response, т.к. уникальны на каждый запрос
2. Финансовые балансы «на запись», т.к. появится риск двойного списания
3. Транзакции

## Где разместить Redis
1. Hot-path Redis (Bidding Service и Delivery Dervice). Необходим отдельный кластер, т.к. необходима максимальная производительность и критичен для SLA 80 мс.
2. Back-office Redis (для Campaign Servie, Analytics Service, кабинета рекламодателя). Менее нагруженный. Не на hor path - деградация не роняет аукцион.

## TTL и стратегия инвалидации
Настройка TTL по правилу: часто меняющиеся данные (бюджеты, кампании) короткий TTL + event-driven обновление. Редко меняющиеся (аналитика) длинный TTL, обновление по истечению TTL.

### Численные TTL по типам данных

| Данные                         | TTL         | Стратегия инвалидации                                     | Допустимая давность (stale age) | Обоснование                                                                                            |
| ------------------------------ | ----------- | --------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Кампания                       | 30 сек      | Event-driven через Kafka                                  | менее 30 сек                    | Кампании меняются часто. 30 сек — компромисс между защитой от невалидных показов и нагрузкой на Redis. |
| Бюджет рекламодателя           | 5 сек       | Event-driven через Kafka. Запись только Financial Service | менее  5 сек                    | Бюджет-чувствительные данные, меняются очень часто. 5 сек — максимум, который не ломает SLA 80 мс.     |
| Баланс (текущий остаток)       | 5 сек       | Event-driven через Kafka, резервирование через Redis      | менее 5 сек                     | Баланс — чувствительные данные, меняются очень часто. 5 сек — максимум, который не ломает SLA 80 мс.   |
| Ставка кампании (bid)          | 60 сек      | Event-driven через Kafka                                  | менее 60 сек                    | Ставка меняется только при CRUD-редактировании кампании.                                               |
| Победитель аукциона            | одноразовый | Удаление после передачи в Delivery Service                | 0 (мгновенное использование)    | Победитель — одноразовое значение.                                                                     |
| Топ-N кампаний (локальный кеш) | 15 сек      | Локальный кеш                                             | менее 15 сек                    | Для работы при потере Redis. Данные устаревают быстро, 15 сек — минимальный компромисс.                |


## Прогрев кеша
1. При старте сервиса
2. Периодическое обновление. Например раз в 10 минут обновляется топ компаний для fallbackhandler
3. При деплое новой версии
4. После сбоя Redis
