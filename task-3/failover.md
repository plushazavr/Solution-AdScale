# Отказоустойчивость
 
## RPO и RTO по сервисам
 
| Сервис / хранилище                      | RPO                                           | RTO                                                   | Как достигается                                                                                                                                                                    |
| --------------------------------------- | --------------------------------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bidding, Ad Server, Delivery            | не применимо                                  | < 1 мин                                               | Минимум 3 инстанса в разных зонах, Kubernetes перезапускает упавшие, балансировщик исключает их из трафика                                                                         |
| Redis (hot path)                        | не применимо: восстанавливаются из источников | < 1 мин при отказе узла, < 15 мин при потере кластера | Реплика у каждого шарда с автоматическим переключением. При полной потере — повторное наполнение из компактируемых топиков Kafka; на это время сервисы работают на локальной копии |
| Kafka                                   | 0 для подтверждённых событий                  | < 5 мин                                               | RF=3, подтверждение от двух реплик, брокеры в трёх зонах                                                                                                                           |
| Campaign (PostgreSQL)                   | 0                                             | < 1 мин                                               | Синхронная реплика, автоматический failover через Patroni                                                                                                                          |
| Financial (PostgreSQL)                  | 0                                             | < 5 мин                                               | Синхронная реплика, Patroni. После переключения — автоматическая проверка сходимости балансов                                                                                      |
| Statistics (ClickHouse)                 | 0 в пределах хранения Kafka (7 дней)          | < 1 ч                                                 | Две реплики шарда. Потерянные данные переигрываются из Kafka                                                                                                                       |
| Analytics (PostgreSQL + Object Storage) | 24 ч для витрин                               | < 4 ч                                                 | Витрины перестраиваются из событий и данных Statistics                                                                                                                             |
 
## Соответствие принципам 12-факторных приложений
 
| Фактор                    | Как выполняется                                                                                                                          |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Кодовая база              | Один репозиторий на сервис, один артефакт разворачивается во всех окружениях                                                             |
| Зависимости               | Явно объявлены и упакованы в контейнерный образ, ничего не берётся с сервера                                                             |
| Конфигурация              | Адреса БД, Kafka, Redis, лимиты и таймауты — в переменных окружения и Secrets Kubernetes, не в коде                                      |
| Сторонние службы          | PostgreSQL, Redis, Kafka, ClickHouse подключаются по адресу из конфигурации, переключение на реплику не требует изменения кода           |
| Сборка, релиз, выполнение | CI/CD‑пайплайн собирает Docker‑образ, выпускает релиз с ним и конфигурацией, а затем разворачивает его в Kubernetes — и pod запускается. |
| Процессы                  | Сервисы в hot path не хранят состояние сами, все данные лежат в Redis, Kafka и БД                                                        |
| Привязка портов           | Каждый сервис сам отдаёт HTTP/gRPC на своём порту                                                                                        |
| Параллелизм               | Горизонтальное масштабирование добавлением инстансов                                                                                     |
| Утилизируемость           | Быстрый запуск (загрузка локального кеша за секунды), сброс буфера продюсера Kafka                                                       |
| Паритет окружений         | Тестовое окружение на тех же версиях PostgreSQL, Redis, Kafka, ClickHouse в контейнерах                                                  |
| Логи                      | Логи в stdout, ELK, Kibana, структурированный JSON                                                                                       |
| Административные процессы | Одноразовые задачи запускаются в окружении релиза                                                                                        |

| Хранилище            | Что бэкапим     | Частота                               | Хранение                 | Куда                                                   | Проверка восстановления                    |
| -------------------- | --------------- | ------------------------------------- | ------------------------ | ------------------------------------------------------ | ------------------------------------------ |
| Campaign PostgreSQL  | WAL + full dump | Full — раз в 24 ч, WAL — каждые 5 мин | 30 дней                  | Object Storage в другом регионе                        | Еженедельно, автоматический тест в staging |

| Analytics PostgreSQL | full dump       | Раз в 24 ч                            | 90 дней                  | Object Storage                                         | Раз в неделю                               |
| Redis (hot path)     | Не бэкапим      | —                                     | —                        | —                                                      | Восстанавливается из Kafka (event log)                |
 
 
## Пошаговый DR план
 
### Сценарий: полная потеря кластера (регион недоступен)
 
| Шаг | Действие | Кто |
| --- | -------- | --- |
| 1 | Обнаружение: мониторинг (Grafana) фиксирует отсутствие health-check от всех инстансов региона | Автоматически |
| 2 | Переключение DNS на DR-регион, DR-кластер | DNS (TTL 30 с) |
| 3 | Активация DR-инфраструктуры: K8s в DR-регионе поднимает поды | K8s |
| 4 | Financial PostgreSQL, активация реплики в DR-регионе. Patroni делает failover. | Patroni |
| 5 | Campaign PostgreSQL, failover на DR-реплику| Patroni |
| 6 | Redis (hot path), чтение eventLog Kafka, заполняет Redis | Инженер / автомат |
| 7 | Локальный кеш в Bidding Service пуст. При первых запросах `RedisReplayer` заполняет top-N кампаний. Fallback — no-bid до прогрева. | Автоматически |
| 8 | Проверка: health-check → `GET /health` возвращает 200 для всех сервисов | Автоматически |
| 9 | Возврат трафика: DNS-запись обновлена, трафик идёт в DR-регион. Наблюдение за метриками 30 мин. | Инженер |
 
**Общий RTO:** 26–56 минут (зависит от размера Redis-кластера и скорости Kafka Replayer).
 
### Потеря одного сервиса (горизонтальный сценарий)
 
| Шаг | Действие | Кто |
| --- | -------- | --- |
| 1 | Балансировщик (Envoy/NGINX) видит failure health-check | Автоматически |
| 2 | Исключение pod из endpoints | K8s |
| 3 | Перезапуск pod по Deployment-рулу (maxUnavailable: 0) | K8s |
| 4 | Новый pod загружает локальный кеш из Redis | Автоматически |
| 5 | Возврат в пул endpoints | K8s |
 
**RTO на один сервис:** < 1 мин (как указано в таблице выше).
 
### Потеря Redis (hot path)
 
| Шаг | Действие | Кто |
| --- | -------- | --- |
| 1 | Bidding Service фиксирует timeout на Redis (таймаут 10 мс) | Автоматически |
| 2 | Circuit Breaker на Bidding Service, Redis размыкается | Автоматически |
| 3 | Bidding Service переключается на локальный кеш (top-N кампаний, TTL 15 сек). Аукционы не проводятся, выдаётся `no-bid`, т.к. без подтверждённого резерва в Redis оплачиваемую ставку выдавать нельзя | Автоматически |
| 4 | Запуск `RedisReplayer` для восстановления Redis из Kafka | Автоматически |
| 5 | Когда Redis доступен, Circuit Breaker half-open → проверка → переключение обратно, Circuit Breaker замыкается | Автоматически |
